## Recovery limits

Before COMMIT: ON_ERROR_STOP and a same-session ROLLBACK/disconnect abort the failing transaction. Earlier committed packages remain installed. Verify actual state; do not rerun absent-only files blindly or remove C1 objects to pass collision checks.

After COMMIT: pause/drain affected application, admin, Auth, job and Storage writes; preserve accepted cases/keys/results/originals and prefer a reviewed forward repair. Revoking finalizer/wrapper EXECUTE alone does not stop direct-table or privileged writers. Keep legacy request_case private. Do not drop columns/functions/bucket/ledger, restore weaker policies, relabel unknown risks, fabricate confidence or delete partial/historical records to force rollback. Removing an empty repair restores the existing missing-component outage, not a functioning system. An exact post-use down migration is unsafe before dependency/data review.

If narrow removal is considered **before any new use**, owner must separately review dependencies, retained original definitions/ACLs and data absence, rehearse the exact reversal with RESTRICT and explicitly approve its security impact. Once new NULL confidence/unknown risks/source references/files or submissions exist, old constraints/removal can fail or lose meaning; forward repair is the default. Storage metadata rollback does not restore bytes; supported Storage API restore must preserve references consistently. A checkpoint restore requires explicit downtime/data-loss approval and reconciliation of every later Auth/business/Storage change. Without PITR/delta capture, later writes cannot be recovered by assumption. Delivered/read notifications and external actions are not undone by SQL rollback.
